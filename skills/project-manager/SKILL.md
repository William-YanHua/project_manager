# 项目规划与管理

围绕用户目标主动完善产品或功能，让用户随时知道项目要达成什么、目前到哪里、接下来做什么。技能通用，项目记录独立保存。

## 项目边界

- 先根据当前工作区和用户指定的位置确定项目根目录。已有 `.project-manager.json` 优先；从子目录查找时不得跨越当前项目的 Git 根目录或已知工作区边界。没有 Git 时以用户指定的项目目录为准，不凭目录名猜测项目归属。
- 根目录不明确或同时涉及多个项目时，先明确本次管理哪个项目，再读写记录。
- 项目原始记录只保存在本项目配置指向的位置，不读取其他聊天来替代记录。跨项目汇总是明确允许的例外：只读已启用项目的管理记录，在个人汇总目录保存待办摘要和提醒配置；不把全文、知识文档或聊天集中保存，不通过总清单修改其他项目。技能安装目录不存项目数据。
- 同一根目录内的多个会话共享一份记录；独立 checkout/worktree 按各自根目录管理，不自动跨目录同步。相同项目名称或复制来的 ID 不构成跨目录访问授权。
- 这是文件级的工作约定，不是操作系统权限隔离。所有命令都显式传入已确定的 `--project-root`。

## 首次启用与目标澄清

1. 阅读现有项目说明和管理材料，复用已确认目标，不反复询问已有答案。没有本技能配置时，只在用户要求启用或管理该项目时初始化。
2. 引导用户说明：项目要解决的问题、交付成果、完成标准，以及影响计划的范围或约束。期限、负责人等未知信息保留“未设定”，不自行编造。
3. 一次优先问最影响计划的少数问题。根据已有信息整理待办草案，说明先后关系，交由用户确认；用户已经明确批准的内容不重复确认。
4. 使用辅助脚本创建项目配置和初始记录，并自动登记到待办汇总。模板中的“待确认”是项目数据的真实状态，不应被当作已批准目标。首次升级已有项目时执行 `task_hub.py sync` 登记；不覆盖原有记录。
5. 提议在该项目实际生效的 `AGENTS.md` 或 `AGENTS.override.md` 中加入会话入口。用户已同意接入时直接补充，保留原有内容；不要覆盖文件或修改全局指令。入口示例见 [references/project-record.md](references/project-record.md)。

目标澄清示例：

> 你希望这个项目最终交付什么？做到什么程度，你会认为它已经完成？
> 如果有必须遵守的时间、技术或范围限制，也请一起说明。

## 围绕目标主动完善产品与功能

用户给出目标后，就开始帮助梳理和完善，不等用户逐项提出需求或追问“下一步做什么”。目标明确时直接沿用；目标仍宽泛时，先给出基于现有信息的具体建议，再澄清最影响当前决策的问题。单次讨论不自动初始化项目记录。

- **找出关键缺口。** 从目标用户、使用场景和期望结果出发，检查实现目标所需的核心流程、必要功能、关键异常和验收标准。只指出当前最影响目标的缺口，说明不解决会带来的影响；把已知事实、推测和建议分清，不把设想当作用户需求。
- **给出有取舍的建议。** 优先推荐能解决核心问题的最小可用方案，说明哪些本轮需要、哪些可后续考虑，以及推荐理由。存在会影响选择的取舍时给出少量备选，不默认添加账号、付费、协作等通用功能，也不一次堆出完整功能清单。
- **把下一步说具体。** 每轮推进优先推荐当前最值得做的一步，说明“做什么、为什么现在做、会产出什么或怎样算完成”。依赖尚未确认的信息时，集中提出最关键的问题；已有答案不重复询问。避免只说“继续完善”或让用户从头安排下一步。
- **根据反馈逐步推进。** 用户确认方向、完成任务、反馈验证结果或出现阻塞后，重新对照目标，调整缺口判断并给出下一步。已有记录时同步更新“建议下一步”；完成标准已经满足时建议验收或收尾，不为延长项目不断增加功能。用户仅要求简短回答或单项修改时，按其范围控制建议。
- **分清建议与执行。** 主动分析、提出草案和建议属于本能力；新增需求、扩大范围或实质改变方案仍先确认。未确认建议放在“待确认事项”，用户采纳后再纳入正式待办。已获授权的工作直接推进，不逐步重复索要同一授权，也不把用户拒绝或推迟的建议继续当作当前下一步。

逐步建议示例：

> 用户：我想做一个个人任务管理工具。
>
> 助手：建议先围绕“记下任务 → 找到现在要做的事 → 标记完成”做第一版。下一步先确定最想解决的问题，这会决定首版重点：你更需要避免漏做任务，还是安排每天的优先级？确认后可以形成一份精简的首版功能清单。
>
> 用户：主要是避免漏做，先不加提醒。
>
> 助手：那建议首版包含任务录入、截止日期、今天与逾期待办、完成标记。下一步建议确认日期规则，因为它决定哪些任务会被看见：可先采用“今天到期和已逾期的未完成任务集中展示，无日期任务单独保留”。你确认后，我会把这条规则写入首版清单，并列出对应的验收条件。

## 每个会话开始

在该项目新会话第一次回复时，正式工作前读取最新记录，提醒当前目标、上次进展、关键阻塞和建议下一步。通常控制在四行以内；没有阻塞就省略该行，不重复列出整份待办。

- 用户已指定本次任务时，说明它对应哪项待办并继续执行，不让提醒变成额外审批。
- 建议下一步不自动授权执行待办。没有具体执行指令时，仍按上节主动给出具体建议或草案，让用户有明确的选择；用户已有授权时直接继续。
- 同一会话无需每轮重复提醒；切换项目时重新读取并提醒。长时间中断后继续旧会话时，重新读取有变化的状态。
- 配置或记录缺失、损坏时如实说明，先找回或修复；不要静默重建并覆盖进度。
- 记录没有近期证据时用“上次记录为……”描述，不把旧状态说成已经核实的当前事实。
- 本节会话提醒发生在收到用户输入并开始响应后。用户设置每日提醒时间后，可另通过 Codex 自动化定时汇总提醒；未设置时不创建任务，也不宣称已有后台提醒。

示例：

> 当前目标：完成第一版原型。
> 上次进展：需求已确认，页面设计待确认。
> 当前阻塞：登录方式尚未确定。
> 建议下一步：确认登录方式，再继续设计。

## 推进与更新

以 [references/project-record.md](references/project-record.md) 的项目记录为唯一进度来源。按项目规模维护目标、当前阶段、待办、待确认事项和简短变更记录；不要为小项目强制拆分复杂阶段。

- 待办使用稳定 ID，例如 `T001`；状态为“待办、进行中、受阻、已完成、已取消”。每项说明交付结果或完成条件，必要时记录优先级和依赖。
- 按实际进展更新：开始执行、取得关键结果、遇到阻塞、用户改变已确认安排时及时保存。辅助脚本保存成功后自动同步本项目的待办摘要；直接编辑 Markdown 后执行 `task_hub.py sync`。不要只等会话结束，因为会话可能中断。
- “已完成”必须附可追溯依据，例如验证结果、产物路径或用户明确确认。代码已写好但所需验证未完成时，不得提前标记完成。
- “受阻”说明阻塞原因及解除条件；取消项保留原因和原 ID；发现回归可重新打开任务并记录原因。不要删除历史任务来掩盖范围变化。
- 在已批准的范围内更新客观状态无需再次询问。新增需求、改变目标、扩大范围、实质改变优先级或方案时先列入“待确认事项”，明确影响，获得确认后再纳入正式待办并执行。
- 用户直接提出的新任务可作为该任务的授权；记录时保留其范围，不把小任务扩展成完整项目重规划。
- 每次写入前重新读取。用读取时的 SHA-256 校验保存，避免其他会话的更新被旧版本覆盖；发生冲突时重新读取并合并，不能强制覆盖。
- 只记录对后续推进有价值的变化，不抄聊天原文，不保存凭据或无关个人信息。

更新示例：

> T002 已完成：原型文件已生成并检查。T003 仍受阻，需要先确认登录方式。

## 跨项目待办与每日提醒

按 [references/collection-and-reminders.md](references/collection-and-reminders.md) 执行以下操作：

- 所有已启用本技能的项目汇总到一份总清单，按项目分组，只显示“待办、进行中、受阻”。项目更新时同步自身摘要，查看总清单或定时提醒前重新读取全部已登记项目；不把待确认草案自动变成已批准待办。
- 首次汇总或用户要求“所有项目”时，从可用项目列表发现本地项目；只登记含 `.project-manager.json` 的项目，不遍历整个磁盘、不初始化未启用项目。远程、不可访问或读取失败的项目明确说明未覆盖，不能把缺失数据解释为零待办。
- 汇总文件是只读派生视图；完成或修改任务要回到对应项目，按其规则处理。汇总保存项目目录、原记录路径、源版本和同步时间，避免同名项目或相同任务编号混淆。
- 用户可通过自然语言设置、修改或关闭每日提醒。时间必须由用户明确指定；默认时区为 `Asia/Shanghai`，其他时区按用户指定。用户没有要求当场设置时，不追问、不默认使用示例时间。
- 每日只维护一条统一提醒自动化；通过 `automation_update` 创建或更新，保留返回的 ID。记录提醒偏好不等于任务已创建，只有调度工具确认后才能报告“已启用”。

使用示例：

> “汇总所有项目待办。” → 刷新已启用项目，按项目展示未完成事项与阻塞。
> “每天上午 9 点提醒我。” → 保存 09:00 / Asia/Shanghai，创建或更新一条每日提醒，并核对工具结果。
> “改为每天晚上 8 点半。” → 更新原提醒为 20:30，不创建第二条。
> “关闭每日待办提醒。” → 暂停原自动化，确认成功后记录为已关闭；待办仍继续收集。

## 验收与收尾

对照目标和完成标准逐项检查，列明结果、证据和遗留事项。任务全部完成不自动等于项目结束；验收通过且用户确认结束后，才将项目状态设为“已结束”。用户要求暂停则标为“已暂停”，保留恢复所需信息；恢复或重新打开项目要记录原因。

项目状态建议使用“规划中、进行中、已暂停、待验收、已结束”。这些是项目状态，与单条待办状态分开。

## 文件与辅助命令

默认项目文件：

- `.project-manager.json`：项目标识和管理记录的项目内相对路径。
- `docs/project-management/PROJECT.md`：可直接阅读的目标、待办和当前状态，是唯一进度正文。
- 生效的项目指令文件：短入口规则，不重复存储进度。

`<skill-dir>` 指本技能所在目录；`<project-root>` 必须是已确定的项目根目录。辅助脚本只依赖 Python 标准库，在支持 `fcntl` 的 macOS/Linux 环境运行。

```bash
python3 <skill-dir>/scripts/project_store.py init --project-root <project-root>
python3 <skill-dir>/scripts/project_store.py read --project-root <project-root>
python3 <skill-dir>/scripts/project_store.py write --project-root <project-root> \
  --input <updated-project.md> --expected-sha256 <sha256-from-read>
```

`read` 返回根目录、项目 ID、记录路径、SHA-256 和完整正文。`write` 替换本项目记录并同步待办摘要，不执行待办、不修改其他项目原记录。汇总失败会单独警告，本项目保存不回滚。初始化已存在配置时只读取校验，绝不重置。

个人汇总目录默认是 `${CODEX_HOME:-~/.codex}/project-manager/`，含 `hub.json` 和 `TODOS.md`；它与技能安装目录分开。测试可通过 `PROJECT_MANAGER_HUB_DIR` 使用隔离目录。

其他环境可直接维护同一份 Markdown，但须在写入前重新读取并合并最新内容；无法可靠处理并发写入时先协调，不能宣称有脚本的并发保护。

此技能负责目标驱动的产品与功能完善，以及项目计划和进度。已有知识沉淀技能负责长期知识、设计结论和正式说明；可引用对应文档，但不另建一份相互竞争的待办清单。
